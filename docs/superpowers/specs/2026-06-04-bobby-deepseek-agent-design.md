## 1. 愿景与北极星

### 1.1 一句话定义
Bobby 是一个**开源、专门为 DeepSeek V4 Flash/Pro 调校**的通用编码 agent。它不是又一个套壳，而是一层**"补偿性外骨骼"**：一边榨干 Flash/Pro 的长处，一边用工程手段死死摁住 DeepSeek 的三个原罪。

### 1.2 核心命题：代码是万能溶剂
在电脑上，用户的绝大多数问题——处理文件、清洗数据、做自动化、搭小工具/小网页——本质都能"写段代码跑一下"解决。Bobby 的交付物是**"被真正解决掉的问题"**，代码只是手段，用户甚至不必关心有没有代码。

### 1.3 三个敌人（整套设计反复围绕"打赢它们"展开）
| 编号 | 敌人 | 表现 |
|---|---|---|
| ① | **解题能力弱** | 给了任务做不到点子上 |
| ② | **说谎 / 强幻觉** | 声称做了其实没做；自审永远通过；编造不存在的 API；明令禁止仍违反还谎称遵守 |
| ③ | **听不懂人话** | 对用户意图理解力差 |

### 1.4 护城河：验证引擎本身就是产品
**越不懂代码的用户，越没能力识破谎言。** 开发者能 review、能抓错；小白完全没招——"蒙混过关"在小白身上 100% 得逞。
因此对 Bobby 而言，"测谎 + 反偷懒"的**验证引擎不是一个功能，它就是产品本身**。
产品承诺一句话：

> **"唯一一个不敢骗你的 agent——哪怕你根本看不懂它干了啥，它也被结构性地逼着把'做对了'的证据摆在你面前。"**

## 2. 设计铁律（不可协商，所有模块都得服从）

- **L1 模型自评无效**：凡模型自己说"我检查过了 / 做完了 / 遵守了"，一律视为**无效证词**，不得作为完成依据。
- **L2 出题人 ≠ 阅卷人**：干活的模型不能给自己鸣哨。验证必须来自外部裁判（确定性工具 / 另一个模型 / 人）。
- **L3 强制留痕，偷懒在结构上不可能**：每一条"声称"都必须附可核查的**物证**；漏做就会缺证据或证据对不上，从而被拦下。
- **L4 意图先行**：在动手前先把"用户到底要什么"显式化、确认化；意图契约同时成为验收标准。
- **L5 默认不信任，逐级授权**：执行默认锁在隔离工作区；危险动作必须过权限闸口。
- **L6 通用范围下按能力分级验证**：不假设每个任务都有硬裁判；能硬验则硬验，不能则降级到留痕 + Pro 复核 + 人类闸口兜底——但**绝不允许"无验证直接放行"**。
- **L7 不许静默通过**：验证失败必须显式处理（重做 / 升级裁判 / 上报人类），不得悄悄当成功。
- **L8 不沿用 Claude/GPT 的提示词套路**：prompt、工具描述、循环都按 DeepSeek 自己的脾气调，避免水土不服。

Bobby 在交互形态与 agent 工程上**对标 Claude Code**（成熟、被验证、Codex 参考资料多），但做两类改造：**保留其骨架**，**叠加 DeepSeek 专属的补偿层**。

| 维度 | 抄 Claude Code 的部分 | Bobby 的改造/新增 |

## 4. 总体架构

### 4.1 四层 + 双前端

```
                ┌──────────────────────────────────────────────┐
                │            ④ 脸面层 Face (双前端)               │
                │   ┌────────────┐        ┌──────────────────┐  │
                │   │  CLI 前端   │        │   完整 GUI 前端    │  │
                │   └─────┬──────┘        └─────────┬────────┘  │
                └─────────┼─────────────────────────┼───────────┘
                          │   Kernel API (UI 无关)    │
                ┌─────────▼─────────────────────────▼───────────┐
                │                  内核 Kernel                    │
                │  ┌────────────────────────────────────────┐   │
                │  │           ① 大脑 Brain (Agent Core)       │   │
                │  │  意图捕获 → 规划分解 → Flash/Pro 路由 →    │   │
                │  │  循环编排 → 上下文/记忆 → 子agent          │   │
                │  └───────────────┬────────────────────────┘   │
                │                  │ 每步产出 Claim + Evidence    │
                │  ┌───────────────▼────────────────────────┐   │
                │  │        ② 良心 Conscience (验证引擎)        │   │
                │  │  证据契约 → 裁判分级(确定性/复现/Pro对抗/  │   │
                │  │  留痕/人类) → 完成闸门 → 反偷懒/反幻觉/禁令 │   │
                │  └───────────────┬────────────────────────┘   │
                │  ┌───────────────▼────────────────────────┐   │
                │  │        ③ 双手 Hands (执行/工具/沙箱)       │   │
                │  │  隔离工作区 → 权限阶梯 → 多语言执行 → 工具集 │  │
                │  └────────────────────────────────────────┘   │
                └────────────────────┬───────────────────────────┘
                                     │
                          ┌──────────▼──────────┐
                          │  ⑨ DeepSeek Provider │
                          │  Flash / Pro / 缓存   │
                          └─────────────────────┘
```

### 4.2 关键架构原则
- **内核 UI 无关**：内核以"库 + 本地常驻服务（daemon）"形态存在，对外暴露一套 **Kernel API（事件流 + 命令）**；CLI 和 GUI 都是它的薄客户端。这是"B：双前端共用内核"的落地方式。
- **一切围绕"任务（Task）"**：用户的一次请求 = 一个 Task；Task 拥有自己的意图契约、工作区、执行轨迹、证据集、验收结论。

### 4.3 一个任务的端到端数据流
```
用户输入(人话)
  → [大脑] 意图捕获：复述+确认 → 生成《意图契约》(含验收标准+禁令)
  → [大脑] Pro 规划：拆成最小步骤 DAG
  → 循环 { 
       [大脑] Flash 执行一步 → 产出 Claim + Evidence
       [良心] 按契约挑选裁判 → 裁决(pass/fail)
       fail → 重做/升级Pro/上报人类   pass → 下一步
     }
  → [良心] 完成闸门：对照《意图契约》逐条核验全部验收标准 + 禁令
  → [脸面] 向用户展示「结果 + 人话版证据」→ 高风险处人类确认
```

## 5. ① 大脑层 Brain（Agent Core）

### 5.1 循环编排器（Orchestrator）
一个显式状态机，驱动 Task 的生命周期：
```
INTENT → PLAN → STEP_EXEC → STEP_VERIFY → (loop) → FINAL_GATE → DELIVER
                    ↑___________fail__________↓
```
- 每个状态可被「人类闸口」打断（计划模式 / 危险动作 / 完成确认）。
- 全程写入 **Task 轨迹（trace）**：每一步的输入、模型、工具调用、证据、裁决，全部留痕、可回放、可审计。轨迹是开源信任的基础，也是 GUI 证据展示的数据源。

### 5.2 Flash/Pro 路由器（核心机制）
**统一了"成本/速度分工"与"出题人≠阅卷人"两件事。**

| 角色 | 模型 | 出场时机 | 说明 |
|---|---|---|---|
| **运动员** | V4 **Flash** | 绝大多数执行步骤 | 便宜、快、干粗活：写代码、改文件、调工具 |
| **阅卷人/教练** | V4 **Pro** | 仅在验证闸口 & 规划 | 贵、强、会推理：拆任务、对抗审查、疑难升级 |

路由策略（默认值，可配置）：
- **规划**用 Pro（解题质量靠前置规划补，打敌人①）。
- **执行**用 Flash。
- **验证**：Tier 0/1 确定性裁判不耗模型；需要模型判断的复核用 Pro（绝不让 Flash 审 Flash，守 L2）。
- **疑难升级**：同一步 Flash 连续失败 N 次 → 升级 Pro 亲自执行。
- **预算护栏**：每 Task 设 token/费用上限，Pro 调用计数可见（GUI 显示"已花多少"）。
- ⚠️ **待核实**：Flash/Pro 的真实模型 ID、上下文窗口、是否支持 reasoning 模式、function calling 格式，全部以 DeepSeek 官方文档为准。

### 5.3 意图捕获子系统（打敌人③：听不懂人话）
**目标**：在动手前把模糊人话变成机器可校验的《意图契约》。
- **复述确认**：把用户请求改写成"我理解你要的是……，做完的标准是……"，请用户确认或纠正。
- **歧义检测**：对请求打"歧义分"，超阈值才追问；追问有**预算上限**（避免无限提问惹烦用户）。
- **《意图契约 Task Contract》**（结构化，JSON）：
  ```jsonc
  {
    "goal": "一句话目标",
    "acceptance_criteria": [          // ← 同时就是验收清单(§6.4)
      { "id": "AC1", "desc": "可机器核验的成功条件", "oracle_hint": "test|run|file|review|human" }
    ],
    "constraints": [                  // ← 用户的禁令(§6.8)，持久后置校验
      { "id": "C1", "desc": "禁止做X", "check": "如何机器检测违规" }
    ],
    "inputs": ["相关文件/数据"],
    "out_of_scope": ["明确不做的"]
  }
  ```
- **关键设计**：**意图契约的 `acceptance_criteria` 直接成为良心层的验收清单**——意图与验证在此闭环。"做完"不再由模型说了算，而是"契约逐条满足"。

### 5.4 规划与分解（打敌人①：解题弱）
- 用 **Pro** 把目标拆成**最小可验证步骤**的 DAG；每步都绑定"这步怎么算成功"。
- 步子越小越好：小步 → 易验证 → 错了早发现，避免"一大坨做完才发现全错"。
- 复杂任务进入**计划模式**：先给用户看计划、确认后再执行（抄 Claude Code 的 plan mode）。

### 5.5 上下文与记忆
- **项目记忆**：工作区内的 `BOBBY.md`（项目约定）、历史意图契约、长期禁令。
- **上下文预算管理**：长任务自动压缩/摘要；用 DeepSeek prompt caching 缓存系统提示+工具描述+稳定上下文（§9.5）省钱。
- **禁令持久化**：用户说过的"禁止X"写入持久存储，每个完成闸门都重新校验（§6.8）。

### 5.6 子 agent
- 用于并行/隔离子任务；最重要的用途是**承载 Pro 对抗审查**（§6.7）——审查者跑在独立上下文，不被运动员的"自我辩护"污染。

## 6. ② 良心层 Conscience（验证引擎）—— 护城河，全文最深章节

### 6.1 核心模型：声称 → 证据 → 裁决
任何一步执行结束，运动员不能直接说"我做完了"，而必须提交一个 **Claim**：
```
Claim = { 我声称完成了什么, 对应哪条 acceptance_criteria, 我附上的 Evidence }
```
良心层据此挑选裁判，产出 **Verdict（pass / fail / need_human）**。

### 6.2 证据契约（Evidence Contract）
证据是**带类型的结构化对象**，不是模型的自然语言自述（守 L1/L3）：
```jsonc
{
  "claim_id": "...",
  "ac_id": "AC1",
  "evidence_type": "test_run | command_output | file_diff | file_exists | 
                    schema_valid | symbol_exists | quote_with_location | 
                    pro_review | human_ack",
  "payload": { /* 真实产物：真实命令、真实退出码、真实stdout、真实diff、真实行引用… */ },
  "produced_by": "tool | flash | pro | human",
  "tamper_check": "由工具/沙箱直接产出，非模型转述"
}
```
**铁规**：`evidence_type` 必须由**工具或沙箱直接生成**，模型不得"代笔转述"证据（否则它会编）。

### 6.3 裁判分级（Oracle Taxonomy，对应 L6 能力分级）
按"硬度"从高到低，**优先用最硬的可用裁判**：

| Tier | 裁判 | 适用 | 例子 |
|---|---|---|---|
| **T0 确定性** | 工具说了算 | 有客观判据 | 单测通过、编译成功、lint/类型零错、文件存在、输出与期望逐字节匹配、JSON schema 校验通过、diff 非空且符合预期 |
| **T1 可执行复现** | 真跑一遍看真实输出 | 能跑出结果 | 真实执行脚本、捕获真实 stdout/退出码/产物文件，与契约比对 |
| **T2 异源模型对抗** | **Pro 审 Flash** | 逻辑/正确性无硬判据 | Pro 扮演找茬审查者，输出缺陷清单（§6.7） |
| **T3 强制留痕逐项核对** | 物证 + 覆盖率 | 无 oracle（如逐字检查稿件） | 强制逐项引出原文+定位+结论，按覆盖率核验（§6.5） |
| **T4 人类闸口** | 人拍板 | 高风险/前几者都不足 | 弹窗让用户确认（§6.9 / §7.5） |

**通用范围（"什么都试"）下的规则**：每条 `acceptance_criteria` 在规划时就标注 `oracle_hint`，良心层据此分配 Tier；**没有任何 Tier 能覆盖的验收条件 = 阻断性配置错误**，必须回到意图捕获重谈，**不允许裸奔放行（守 L6/L7）**。

### 6.4 完成闸门（Completion Gate）—— 反"蒙混过关"的总闸
状态机层面，Task **无法**进入 `DELIVER`，除非：
1. 《意图契约》中**每一条** `acceptance_criteria` 都有 **pass 的 Verdict**；
2. **每一条** `constraint`（禁令）后置校验通过；
3. 任何 `need_human` 项都已获人类确认。
否则 Task 状态只能是 `FAILED` 或 `BLOCKED`，**绝不能显示"已完成"**。
> 这一条直接铲掉你最痛的场景："它自审总通过 / 没仔细看就说检查完了"。在 Bobby 里，"看起来完成"和"真的完成"被强制等同。

### 6.5 反偷懒机制（针对"没仔细看完就说检查完了"）
当任务是"逐项处理 N 个对象"（逐行查稿、批处理 100 个文件、逐条核对）：
- **强制分块 + 逐块留痕**：每个对象/每行必须产出独立证据条目（引出原文 + 定位 + 结论/修改）。
- **覆盖率追踪**：系统统计"已留痕对象数 / 应处理对象数"；不足 100% → 闸门判 fail，禁止声称完成。
- **抽样复核**：Pro 随机抽 K 个对象独立重做，与 Flash 结论比对；不一致率超阈值 → 整批打回。
- 结果：**漏看在结构上必然缺证据，从而被拦下**（守 L3）。

### 6.6 反幻觉机制（针对"编造 + 说谎"）
- **先读后断言（grounding）**：凡引用文件/符号/数据，必须先有真实读取证据；无证据的断言被拒。
- **符号存在性校验**：调用的 API/函数/导入，必须经 `symbol_exists` 工具确认真实存在，杜绝"编个不存在的函数"。
- **来源标注**：结论必须可追溯到工具产出或文件位置；"凭空结论"判 fail。

### 6.7 Pro 对抗审查协议（T2 的具体契约）
- **角色设定**：Pro 是**带敌意的审查者**，KPI 是"找出 Flash 的错"，不是"鼓励"。提示词明确："默认存在缺陷，请尽力证伪其完成声称。"
- **独立上下文**：审查者不读 Flash 的"自我辩解"，只读：意图契约 + 真实产物（diff/输出/文件）。
- **结构化产出**（JSON）：
  ```jsonc
  {
    "verdict": "pass | fail",
    "defects": [
      { "severity": "critical|high|medium", "ac_id": "AC1",
        "evidence": "我看到的具体问题位置/复现", "must_fix": true }
    ],
    "unverifiable": ["我也无法判定的点 → 升级人类"]
  }
  ```
- **裁决规则**：任何 `critical/high` 缺陷 → fail，打回重做。审查者说不准的 → 转 T4 人类。
- **防共谋**：审查者与执行者**不同温度/不同 system prompt/不同模型层级（Pro vs Flash）**，最大化"出题人≠阅卷人"。

### 6.8 禁令执行（针对"明令禁止仍违反还谎称遵守"）
- 用户的每条"禁止X"在意图捕获时转成 **constraint**，并尽量给出**机器可检测的 `check`**（如"禁止改动 `src/legacy/`" → diff 路径过滤器；"禁止联网" → 沙箱网络拦截 + 调用审计）。
- **每个完成闸门都重新跑全部 constraint 校验**，不是只在 prompt 里写一句就算数。
- 无法机器检测的禁令 → 自动转 Pro 复核或人类闸口。
- 结果：禁令从"口头嘱咐"升级为"结构化后置条件"，违反必被抓。

### 6.9 验证失败的处理（守 L7）
```
fail → 归类原因 → 
   可自动修复 → 回 STEP_EXEC 重做（计入重试预算）
   反复失败   → 升级 Pro 亲自执行
   仍失败/高风险/不可判 → BLOCKED + 上报人类，附完整证据
```
**永远不允许把 fail 静默改写成 pass。**

## 7. ③ 双手层 Hands（执行 / 工具 / 沙箱）

### 7.1 隔离工作区
- 每个 Task/项目有专属工作目录；默认**只读写工作区内部**。
- 工作区外访问、全盘读写 = 危险动作，需过闸口。

### 7.2 权限阶梯（隔离工作区 + 权限闸口，对应你的选择）
| 级别 | 动作 | 默认策略 |
|---|---|---|
| L0 | 工作区内读 | 自动允许 |
| L1 | 工作区内写/改 | 自动允许（留 diff 证据） |
| L2 | 在工作区内执行代码 | 自动允许（沙箱内） |
| L3 | 装包 / 写工作区外 / 删除 | **弹窗确认** |
| L4 | 联网 / 访问系统敏感区 / 全盘 | **弹窗确认 + 默认拒绝** |
- 策略可在配置里收紧/放松；GUI 给小白更保守的默认。

### 7.3 工具集（每个工具的产出都要能当证据）
- 文件：读/写/改/列目录/搜索（grep/glob）
- 终端：受控执行（沙箱 + 超时 + 资源上限）
- **代码执行器（多语言）**：TS 内核通过子进程跑 Python/shell/node/… —— agent 自身是 TS，但解决用户问题用任意语言
- 测试/质检：test runner、linter、类型检查、编译（喂 T0 裁判）
- 校验工具：diff、文件存在、schema 校验、符号存在性（喂证据契约）
- Web（L4 受限）：抓取/检索，默认关闭，需授权

### 7.4 多语言执行
- 内核维护"语言运行器"注册表（python/node/bash/…），探测本机可用解释器；缺失时按 L3 走"装包确认"。
- 所有执行经沙箱包装：限定 cwd、超时、内存/进程上限、网络默认关。

### 7.5 危险动作与弹窗
- 维护**危险动作清单**（删除、覆盖、装包、联网、改工作区外、长耗时）。
- 命中即暂停，向当前前端（CLI/GUI）抛"授权请求"，附**这一步要干啥 + 影响范围**，等人确认。

### 7.6 插件 / MCP 扩展系统（v1 内置）
- **目标**：让社区与用户在不改内核的前提下扩展工具能力。
- **工具插件 SDK**：统一工具接口（`name` / `description` / `inputSchema` / `run()` / `permissionTier` / `evidenceProducer`）。第三方工具与内置工具一视同仁，**同样必须产出结构化证据**（守 L1/L3——插件不得成为"绕过验证"的后门）。
- **MCP 客户端**：内置 MCP 协议客户端，可挂载外部 MCP server 作为工具来源；挂载来的工具自动套用权限阶梯（§7.2）与证据契约（§6.2）。
- **加载与隔离**：声明式注册（配置列出启用项）；插件的危险能力默认走 L3/L4 闸口。
- **仓库**：`packages/shared` 暴露插件类型；`packages/kernel` 提供加载器与 MCP 客户端。

### 7.7 可选强沙箱模式（v1 内置，默认关）
- 默认 = 隔离工作区 + 权限阶梯（轻量、小白零配置）。
- **v1 同时内置一个"强沙箱"开关**：检测到本机有容器运行时即可一键启用容器 / 微 VM 隔离，给高敏感场景更硬的边界。设计与实现都在 v1 完成，默认关闭——不是"将来再做"。

## 8. ④ 脸面层 Face（同内核双前端）

### 8.1 内核接口 Kernel API（CLI 与 GUI 的唯一契约）
内核以**本地常驻服务 + 库**两种形态提供同一套接口：
- **命令**：`startTask(input)`、`answer(taskId, reply)`、`approveGate(gateId, decision)`、`abort(taskId)`、`getTrace(taskId)`…
- **事件流**（订阅式）：`intent_proposed`、`plan_ready`、`step_started`、`tool_called`、`evidence_produced`、`verdict`、`gate_request`、`final_result`、`error`…
- CLI 与 GUI **都只消费这套接口**，不得各写一套逻辑（守 DRY，保证两端行为一致）。

### 8.2 CLI 前端（完整）
- 终端体验对标 Claude Code：流式输出、可见的工具调用、权限弹窗、计划模式、可中断，外加会话恢复、任务历史、配置子命令、无头 / 脚本模式。
- 面向开发者 / 半技术用户；与 GUI 共用内核、能力对等（见 §8.6），不是 GUI 的残缺子集。

### 8.3 GUI 前端（完整产品级，面向含小白在内的各类用户）
> 不做"残缺极简版"。一个能上线、能辐射小白的产品该有的界面，**v1 全部做完**；核心交互如下，完整界面清单见 §8.6。
- **对话式主界面**：用户说人话 → 看到"它在干什么"的步骤流 → 看到结果 + 证据。
- **意图确认卡片**："我理解你要……，做完的标准是……，对吗？"（可编辑纠正）。
- **权限 / 危险动作弹窗**用大白话："它想联网下载一个工具，允许吗？"
- 与 CLI 共用内核，行为一致。

### 8.4 证据可视化（小白也能"看见它没骗人"）—— 护城河的临门一脚
- 把结构化证据翻译成**人话 + 可点开的硬证据**：
  - "✅ 我处理了全部 100 个文件（点开看清单与逐个结果）"
  - "✅ 我跑了你的检查脚本，0 错误（点开看真实运行输出）"
  - "✅ Pro 复核：通过（点开看它挑过哪些刺）"
  - "⚠️ 有 1 处我不敢保证，需要你看一眼"
- **核心**：小白看到的不是"我做完了"，而是"做完了 + 这是证据 + 哪里还不放心"。这正是产品承诺的兑现处。

### 8.5 双前端如何共用内核
- 内核打包为可独立运行的本地 daemon（亦可作为库内嵌）。
- CLI = 瘦客户端连 daemon；GUI（Electron 渲染层）= 另一个瘦客户端连同一 daemon。
- 一份内核，两张皮，零逻辑重复。

### 8.6 完整界面清单（v1 全部交付，非延期）
> 以下是"一个能上线、能辐射小白的产品"必备界面——它们**不是 v2，而是 v1 的一部分**：
>
> **首启 / 上手**：首次运行向导（引导拿并填 DeepSeek Key、选默认权限档、选语言）；环境健康自检（Key 可用性、本机 python/node 等运行器、可选容器运行时）。
> **主工作区**：任务对话区 + 实时步骤流（intent→plan→step→evidence→verdict 全程可视）；计划模式视图（执行前看 Pro 拆的步骤 DAG，可批准 / 改 / 拒）；证据面板（§8.4，每条"完成"可点开看硬证据）；闸口确认区（危险动作 / need_human / 完成确认）。
> **项目 / 历史**：工作区管理（新建 / 切换 / 打开本地目录作隔离工作区）；任务历史（查看完整轨迹 trace、复用、重跑）；结果产物浏览（直接看产出的文件 / diff / 报告）。
> **设置**：Key 管理（OS keychain）、模型与路由（Flash/Pro 默认、reasoning 开关、预算上限）、权限阶梯默认档、强沙箱开关（§7.7）、插件 / MCP 管理（启用停用、查看插件权限，§7.6）。
> **全局**：成本 / 用量显示（本次 / 累计 token 与费用、Pro 调用次数）；主题（亮 / 暗皆用心）；多语言（至少中 / 英）；帮助 / 错误面板（报错给人话解释 + 下一步建议，错误入轨迹不静默吞）。

## 9. DeepSeek 协议级适配（§1.3 之 B 类适配 / 守 L8）

> ⚠️ 本章所有协议细节**实现前必须对照 DeepSeek 官方文档核实**，本文档不臆测具体字段。

### 9.1 模型矩阵
- **V4 Flash** = 运动员（执行）；**V4 Pro** = 阅卷人/教练（规划、对抗审查、疑难升级）。
- 待核实：模型 ID、上下文窗口、定价、限流。

### 9.2 Function / Tool Calling
- 按 DeepSeek 的 tool calling 格式实现工具协议；**不照搬 Claude/OpenAI 的字段习惯**（守 L8）。封装一层适配器隔离差异。

### 9.3 结构化输出 / JSON 模式
- 意图契约、规划 DAG、证据、Pro 审查结论**全部走结构化输出**，降低解析脆性与幻觉。

### 9.4 FIM（填空补全）
- 若 DeepSeek 提供 FIM，代码局部编辑优先用 FIM（更省、更准）；否则回退普通补全。

### 9.5 Prompt Caching（省钱关键）
- 缓存稳定前缀：系统提示 + 工具描述 + 长期上下文，降低 Flash 高频执行的成本。

### 9.6 推理模式开关
- Pro 在规划/对抗审查时开启 reasoning（如可用）；Flash 执行时关闭以提速降本。

### 9.7 DeepSeek 专属提示词工程
- system prompt、工具描述、few-shot 全部按 DeepSeek 的脾气**重写并实测**，不复用别家模板。建立一套针对三个敌人的提示词回归用例。

### 9.8 Provider 抽象层
- 薄抽象，**v1 即完整实现**：DeepSeek 为唯一随产品发布的 provider；适配接口本身做完整，使"新增一个 provider"沦为"写一个 adapter + 配置"的事，而非重构。这是 v1 内完成的边界设计，不是延期项。

### 9.9 错误 / 限流 / 重试
- 统一的退避重试、限流处理、超时；失败要进 Task 轨迹，不得静默吞掉。

## 10. 配置、Key 管理、隐私

- **BYO Key**：用户填自己的 DeepSeek API Key，本地安全存储（OS keychain 优先）。无服务器、无账号、无计费（对应"开源 + 自带 Key"）。

- **配置**：项目级 `BOBBY.md` + 全局配置（默认模型、预算上限、权限默认、禁令库）。

## 13. 风险与未决问题

| 风险 | 说明 | 应对 |
|---|---|---|
| **通用范围验证缺口** | "什么都试" → 部分任务无任何 oracle | L6 强制：无裁判即阻断重谈，绝不裸奔；T3/T4 兜底 |
| **Pro 成本** | 对抗审查 + 规划频繁用 Pro 会贵 | 预算护栏 + 缓存 + 仅闸口用 Pro + 可调采样率 |
| **DeepSeek 能力假设** | FIM/缓存/reasoning/tool 格式是否如设想 ⚠️ | M6 前先做一轮 DeepSeek 能力探针实测，再定细节 |
| **沙箱安全边界** | 隔离工作区非强沙箱，仍有逃逸风险 | 权限阶梯 + 危险动作弹窗 + 默认拒网；**v1 内置可选强沙箱模式**（§7.7，默认关、可一键开） |
| **GUI 工作量大** | 完整双前端 + 全套界面(§8.6) 工作量大 | 用共享内核(§8.1/§8.5)消除两端逻辑重复来摊薄；按 §12 里程碑分阶段交付，但**范围不缩、不延期到 v2** |
| **审查者共谋** | Pro 审 Flash 仍同厂同源 | 不同层级/温度/独立上下文/敌意提示；高风险再加人类闸口 |

**已拍板（2026-06-04）**：
1. License = **Apache-2.0**（AI/agent 领域的专利授权条款比 MIT 更稳妥）。
2. GUI = **Electron**（与 TS 内核同栈、Codex 参考多、双前端共享最顺、落地风险最低；Tauri 更轻但 Rust 摩擦大，弃）。
3. 插件 / MCP 扩展点 = **纳入 v1**（见 §7.6）。
4. **无 v2**：以上及全文所有能力均在 v1 一步到位。

## 14. 术语表
